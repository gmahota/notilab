## 2026-08-31 — Agent Management API (external AI agents as editors)

Context: NotiLab is to be operable by an external AI agent (initially Abacus.ai) acting as an **editor**, not a developer — no code changes, no direct database access, everything through NotiLab's business rules.

- **Decision**: External agents get their own surface at `/api/agent/*` with its own authentication (static API key, environment only), separate from `lib/admin-auth.ts`. Reusing the human JWT/cookie path would have meant either handing an agent a person's session or teaching the login surface to accept bearer tokens — both enlarge the human auth surface, which is the opposite of the goal.
- **Decision**: Capabilities are a **compile-time registry** of declared tools (`lib/agent/registry.ts`), each with a name, description, input schema, output schema, permission set and audit action. No generic `/execute`, no endpoint taking an instruction, no dynamic registration. Adding a capability is a reviewed commit. `/api/agent/tools/[tool]` is a dynamic route only as transport — the name is in the URL and resolves solely against the registry.
- **Decision**: A new business layer, `lib/editorial/`, owns the article lifecycle, the editable-field whitelist and the publish gate. Route handlers stay thin (AGENTS.md § Next.js Rules) and a future admin UI can reuse it. This is where "an article reaches PUBLISHED only from APPROVED" lives, so it holds for every caller rather than per-route.
- **Decision**: Own ~200-line validator (`lib/agent/schema.ts`) instead of adding zod. AGENTS.md § Dependency Policy prefers what is installed, and the module has to emit JSON Schema for OpenAPI/capabilities anyway — one declaration that both validates and advertises cannot drift.
- **Decision**: **No Prisma schema change.** Local and production share one Neon database and deploys do not run `prisma migrate deploy` (see `prod-db-differs-from-local` / `prod-deploys-bypass-ci` context), so a migration is a manual production operation. Consequences, all documented in `docs/agent-api.md` § Limitations rather than worked around: SEO maps onto `slug`/`title`/`summary` because no `seoTitle`/`seoDescription` columns exist; scheduling is stored as append-only intent rows in `AdminAction` (`resource: ARTICLE_SCHEDULE`) rather than a `scheduledFor` column; idempotency reuses `AdminAction` and therefore has a millisecond-wide race with no `@@unique` to close it.
- **Decision**: Audit reuses `AdminAction` (it already exists for this, and has no FK to `users`, so `userId = "agent:<id>"` works without an agent impersonating a person). Failed and refused writes are audited too. A failed audit write never fails the request — it surfaces as `meta.auditRecorded: false`.
- **Decision**: "Highlight" (editorial prominence) maps to `News.priority` (authored), **not** `News.trending`. `business-rules.md` requires `trending`/`rankingScore`/`importanceScore` stay derived from real signals; no tool can write them.
- **Decision**: `/api/cron/publish-scheduled` is written and tested but **deliberately not registered in `vercel.json`**. It is the only cron that would publish to the public site unattended; enabling it is an operator decision.
- **Decision**: Default permissions with no configuration are `readonly`. A forgotten env var must under-grant, never over-grant.
- **Known trade-off, accepted**: granting one credential both `article.review` and `article.publish` lets that agent approve and publish its own drafts. Splitting drafting and publishing across two credentials is the operator's call, documented rather than forced.
- **Known gap, not fixed here**: `GET /api/news` has no `status` filter, so it returns drafts and archived articles. Pre-existing; it means `unpublish_article` does not remove an article from that one endpoint. Fixing it changes public behaviour and was kept out of scope.

## 2026-08-31 — Clearing the dependency audit CI gate

Context: `Dependency Vulnerability Audit` (`pnpm audit --audit-level=high` in `.github/workflows/security.yml`) had been failing on every PR — 20 advisories, 12 of them high. It was failing on PR #96 too, so it was being merged past rather than acted on. A permanently red required check trains people to ignore red checks, which is the actual cost.

- **Decision**: Bump `next` 15.5.19 → 15.5.25 (and `eslint-config-next` to match). Three of the twelve highs were in Next.js itself and directly relevant to a public site: DoS in the App Router via Server Components, SSRF in Server Actions, SSRF in rewrites. Patch-level bump inside 15.5.x.
- **Decision**: The remaining nine are transitive and pinned with `pnpm.overrides` rather than by waiting for upstream:
  - `postcss@8` → `^8.5.26` (arbitrary file read; path traversal via `sourceMappingURL`)
  - `nanoid@3` → `^3.3.18` (infinite loop with custom generators)
  - `js-yaml@4` → `^4.3.1` (quadratic CPU on `!!omap`)
  - `brace-expansion@1` → `^1.1.18` and `brace-expansion@>=4 <6` → `^5.0.9` (unbounded expansion DoS; the two major lines are affected separately, hence two range-scoped keys rather than one blanket override that would force v5 onto v1 consumers)
  - `sharp` → `^0.35.0` (inherited libvips advisories)
- **When to remove an override**: when the direct dependency that pulls the package in has itself moved past the patched version. An override that is no longer doing anything is worse than none — it silently pins a transitive dependency and nobody remembers why. `pnpm why <pkg>` shows whether it is still needed.
- **Result**: `pnpm audit` reports no known vulnerabilities. Verified with lint, typecheck, tests and a production build after the bump, since `sharp` is a native module and a `next` bump can break a build.
- **Not fixable in a commit**: `Dependency Review` fails with *"Dependency review is not supported on this repository. Please ensure that Dependency graph is enabled."* The dependency graph is off (the SBOM endpoint 404s) — a repository setting under Settings → Code security, not anything a PR can change. Deliberately did **not** soften the workflow with `continue-on-error` to make CI green: weakening a security check to hide a configuration gap is the wrong trade. `dependabot_security_updates` and `secret_scanning` are also disabled, which is why these advisories accumulated unnoticed in the first place.
- **Licence exemption, needs ratifying**: bumping `sharp` moves `@img/sharp-libvips-*` from 1.2.4 to 1.3.3, and `Dependency Review` rejects them as LGPL-3.0-or-later. The exposure is **not new** — `main` already ships 1.2.4 under the same licence, for as long as Next.js has been a dependency. It surfaced now for two reasons that coincided: the version change makes the packages "changed" in the PR diff, and dependency review only started working at all once the repository dependency graph was enabled. Exempted by package name (`allow-dependencies-licenses`) rather than by widening `deny-licenses`, so the next LGPL-3.0 package is not silently accepted too. LGPL permits use without the copyleft reaching this application and these are unmodified upstream binaries, but that is a licensing judgement rather than a technical one — recorded here so it is a decision someone made, not an accident.
- **Repository settings enabled** (2026-08-31, via API, with the owner's approval): Dependency graph, Dependabot security updates, secret scanning and secret scanning push protection. All four were off, which is why twelve high-severity advisories accumulated without anyone being told and why `Dependency Review` had never once run successfully.

## 2026-09-03 — Closing quality-gate items 5, 13, 20

Context: roadmap items 5 (quality-gate gaps), 13 (ranking/AI test coverage) and 20 (`sync-news` rate-limit overrun). Two of the three turned out to be partly or wholly stale: a Jest suite had been added during the Agent Management API work while `AGENTS.md`, `QUALITY_GATE.md` and `lessons-learned.md` all still said no suite existed, and #20's cadence fix had already shipped without the entry being closed.

- **Decision**: `@typescript-eslint/no-explicit-any` and `no-unused-vars` go from `"off"` to `"warn"`, not straight to `"error"`. There are 81 pre-existing violations across 37 files; flipping to `"error"` means either a 37-file diff (against `AGENTS.md`'s ~20-file PR guidance) or a red required check. `"warn"` is strictly stricter than `"off"`, so it satisfies the baseline rule, and it makes the backlog visible in every lint run instead of invisible. Promotion to `"error"` is a follow-up gated on clearing the backlog.
- **Decision**: `no-unused-vars` is configured with `argsIgnorePattern`/`varsIgnorePattern`/`caughtErrorsIgnorePattern` of `^_`. Without an escape hatch the rule has no legitimate way to express a deliberately-unused binding, and people reach for `// eslint-disable` instead, which suppresses more than intended.
- **Decision**: `app/api/news/route.ts` is the reference module for the lint backlog. It carries exactly one of each violation shape (unused type, `any`, unused caught error) and is covered by `__tests__/api/news/route.test.ts`, so the fixes are verifiable. The other 36 files are deliberately untouched.
- **Finding while fixing it**: the `any` on the `news.map()` callback was masking a real type mismatch — the endpoint's unused hand-written `NewsItem` type declared `priority?: number`, but `News.priority` is the `Priority` enum, so the response has always carried a string there. Dropping the annotation restores Prisma's own inference (which tracks the schema) rather than replacing it with another hand-maintained type. **Runtime output is unchanged**; consumers expecting a number were already getting a string. Not fixed here — changing the response shape is a separate, breaking decision.
- **Decision**: `.lighthouserc.json` is **removed**, not wired into CI. It had never been referenced by any workflow. Wiring it means adding Lighthouse CI, and `AGENTS.md` § Dependency Policy puts new CI tooling behind an explicit discussion; it would also need a running server and a database in CI. Its intent is preserved here so the file's removal does not lose it: performance ≥ 0.75, best-practices ≥ 0.85, SEO ≥ 0.85, FCP ≤ 3s, LCP ≤ 4s, TBT ≤ 500ms as warnings; accessibility ≥ 0.90 and CLS ≤ 0.1 as errors; against `/`, `/feed`, `/trending`. Recoverable from git history if Phase 2 adopts it.
- **Decision**: `lib/ranking.ts` is the reference module for test coverage — pure arithmetic, no DB, and it decides the order of every feed in the product. 42 cases added. `lib/ai-processing/*` and `lib/trends.ts` are the next batch and remain uncovered.
- **Pinned as current behaviour, not endorsed**: two ranking behaviours are now locked in by tests so that changing them is a recorded decision rather than a silent drift. (1) Trend matching is bidirectional substring containment (`kw.includes(tag) || tag.includes(kw)`), so the tag `ai` matches a `spain` trend — the same class of over-broad matching that produced the ingestion noise problem. (2) The still-trending longevity bonus is effectively binary: `base` only takes the values 0 / 33.3 / 66.7 / 100, and both values above the 60 threshold multiply to ≥ 100, so the 1.5x multiplier can never yield an intermediate score.
- **Item 20 needed no code change** — `vercel.json` already runs `sync-news` once daily (10 queries = 10 GNews req/day, inside the 100/day free tier), and the Hobby plan rejects sub-daily cron expressions at deploy time regardless. Only the `lib/ingestion/providers.ts` docblock was stale: it still described a `*/30` schedule and 480 req/day as a live problem. A comment describing a fixed problem as current is worse than no comment — the next reader re-opens closed work.
- **Not done, deliberately**: `pnpm test` is still not a CI job. `ci-cd.yml` is CODEOWNERS-protected and the gate baseline is a reviewed decision, so raising it is not a mid-task edit. This is the top follow-up — without it the suite can rot silently.
- **Not done, deliberately**: `lib/user-service.ts` and `lib/social-service.ts` are dead code — zero callers, and `user-service` fetches five endpoints that do not exist (`/api/user/personalized-feed`, `/reading-activity`, `/points`, `/achievements`, `/leaderboard`). They were the first-choice reference module until that surfaced. Deleting them is a separate change.

## 2026-09-04 — Recording the English-code / Portuguese-content language convention

Context: the repo had drifted into mixed-language documentation and comments (roadmap #23–#32), and an audit found the convention had never actually been written down anywhere — it was being re-decided ad hoc, file by file, by whoever touched it.

- **Decision**: English for all code, identifiers, type/interface names, code comments, `prisma/schema.prisma` (models, fields, enums, comments), file/directory names, environment variable names, commit messages, all documentation, and developer/operator tooling output (a script's `console.log` status text is developer-facing). Portuguese is reserved for user-facing content only: article bodies, AI-generated `summary`/`tldr`/`whyItMatters`/`explainLikeIm10`/`titleTranslated`, UI copy/labels rendered to readers, `aria-label`s, and end-user-facing API error messages. The dividing line is who reads the string. Recorded in `AGENTS.md` § Language Rules so it is enforceable, not just documented in a PR description.
- **Decision**: `ProfileType` enum values (`JOVEM`, `EXECUTIVO`, `ESTUDANTE`, `SENIOR`) and category slugs (`mocambique`, `africa-do-sul`, `filmes`, `ciencia`) are a **deliberate exception** and stay Portuguese — they are persisted database values, not identifiers. Renaming the enum requires a backfill of every `user_profiles` row; renaming slugs is a real data migration. Both encode a product rule, so either change needs `02-editorial-content` sign-off, and there is no isolated environment to rehearse it in since local and production share one Neon database (see `prod-db-differs-from-local`). These must not be picked up as cosmetic cleanup under this convention.
- **Audit finding**: `prisma/schema.prisma` was already fully English in every model, field, and enum *name* — zero Portuguese identifiers were found anywhere in the codebase. The gap was entirely documentation prose, one Portuguese directory name, scattered code comments, and operator-facing console strings in two scripts — all remediated under roadmap #24–#32.
- **Refinement (roadmap #35)**: natural-language example prompts in API documentation are **content, not prose**, and stay Portuguese, even inside an otherwise-English document. Task #24 translated 8 example user prompts in `docs/agent-api.md` (e.g. `"Mostra as notícias ainda não publicadas."` → `"Show me the news that hasn't been published yet."`) — an independent review and a second pass both judged this an over-translation, reverted in full in roadmap #35. The "who reads the string" test from the decision above still applies, but these strings are also *produced* by a Portuguese-speaking editor typing into a Portuguese-language product, so they are representative content rather than developer explanation, the same category as UI copy. The concrete evidence for the defect: `lib/agent/tools/articles-read.ts:5`'s docblock quotes `"encontra notícias sem imagem"` as the example query the tool-matching logic was designed around, correctly left in Portuguese — so before this fix the doc demonstrated the API in English while the code demonstrated the same feature in Portuguese, a live contradiction between two descriptions of one feature. English explanatory clauses that sit on the same line as a reverted prompt (e.g. `— \`priority\` is the authored prominence field...`) stay English; only the quoted prompt text reverts.

## 2026-09-04 — Identity model: three human tiers, one session, metered AI

Context: `/profile` was found to be entirely mock data (four client components with module-level `const` arrays), reader authentication did not exist at all, and every user endpoint trusted a client-supplied `userId`. This entry is the `01-cto` sign-off that roadmap #30 was waiting for, and the strategy that mission M1 (#38–#59) implements.

- **Decision**: **One session, one cookie, role as an attribute.** A single `lib/auth/session.ts` exposes `getSession() → { userId, role } | null`; `checkAdminAuth()` becomes a thin role-gate over it rather than a parallel auth system. Staff are readers who additionally have `/admin` — a `REDATOR` reads the site as themselves. Rejected: a second reader-side cookie beside `admin-token`, which would mean two session lifetimes, two revocation paths, and two places to get expiry wrong.
- **Decision**: The machine surface stays separate. `/api/agent/*` keeps its static-API-key path (`lib/agent/auth.ts`) and its `agent:<id>` audit attribution — bots get no `User` row and no session, upholding the 2026-08 decision above. Agents are *actors* in the AI ledger but never identities in the session layer.
- **Decision**: **Auth.js v5 + Prisma adapter. Magic-link for readers, password for staff only.** What makes reader auth risky is not login but email verification, session revocation and rotation; hand-rolling those on the existing 8-hour `jsonwebtoken` cookie makes each of them our bug. Magic-link means readers have no password at all, which removes the entire reset/breach surface. Staff keep credentials because they need deterministic login, but against `User.password` in the database with a real per-user hash. Reversibility requirement: all consumption goes through `lib/auth/session.ts` so the provider can be swapped without touching every call site — Auth.js v5 is still pre-1.0.
- **Decision**: **Three human tiers, written down.** Visitor (anonymous, `getAnonSessionId()`), Reader (`USER`), Staff (`REDATOR`…`SUPER_ADMIN`). The matrix lives in `business-rules.md` and the code reads from it, replacing the inline role array at `lib/admin-auth.ts:20`.
- **Decision**: **Identity is derived server-side; `userId` is removed from all client input.** `GET /api/user?userId=` becomes `GET /api/me`. This is simultaneously a breaking API change and a security fix, so it ships one endpoint per PR rather than gradually — a half-migrated endpoint is indistinguishable from the vulnerability.
- **Decision**: **Visitor is a designed state, not a fallback.** `/profile` for an anonymous visitor renders the value proposition and sign-in — never a 404, and never fabricated statistics. Rejected explicitly: pointing the four profile components at `/api/user?userId=<demo user>`, which would make the page look real while deepening the access-control defect.
- **Decision**: **AI spend is metered at the single egress point.** `lib/ai-processing/call-ai.ts` is the only path to a provider (five call sites) and today it discards the provider's `usage` object entirely, so no spend is attributable to anyone. `callAI` gains a **required** actor (`user:<id>` | `agent:<id>` | `system:<cron>`), returns `usage`, writes an `AiUsage` row, and refuses before the call when the actor is over quota. Enforcement is a pre-call estimate reconciled against the post-call actual, because the estimate never matches. A per-user cap is paired with a **global monthly ceiling and kill-switch** — per-user limits do not protect against many users. Over-quota fails *open* for staff and *closed* for visitors, and every rejection names the limit and the reset time.
- **Finding that motivated the above**: `/api/chat` has no authentication and no rate limiting, and calls `gpt-4o-mini` at 700 `max_tokens` per request. It is a public, unmetered LLM endpoint. Rate-limiting it and adding the global ceiling do **not** depend on the identity work and ship first, in mission phase 0.
- **Deliberately out of scope**: social login beyond one provider, organization/team accounts, paid tiers and billing, staff 2FA, SSO, migrating `/api/agent/*` onto the new session, and redesigning the gamification rules themselves (`02-editorial-content` owns whether the scoring is *correct*; M1 only makes it *real*).
- **Delivery risk recorded here because it can invalidate the whole plan**: `prisma migrate deploy` never runs in production (the deploy job has no `VERCEL_TOKEN` — see `prod-deploys-bypass-ci`), and local and production share one Neon database (`prod-db-differs-from-local`). The new session tables are additive and safe in shape, but a login flow depending on tables production does not have is worse than the current mockup. Phase 1 does not start until migration delivery has a plan.

## 2026-09-04 — Reversal: the AI quota subsystem is cancelled

This **supersedes the "AI spend is metered at the single egress point" bullet** in the M1 identity entry above, recorded earlier the same day. That bullet is left in place rather than edited, so the reversal is visible as a reversal. Roadmap #53, #54, #55 and #56 move to `cancelled`; #40 is rescoped.

- **Decision**: `/api/chat` gets **no per-user rate limit and no per-user quota**, and no `AiUsage` ledger, global ceiling or kill-switch is built. The cost arithmetic does not support them: the providers are `gpt-4o-mini` and `llama-3.1-8b-instant` at `MAX_TOKENS = 700`, which is on the order of $0.001 per message. Capping readers is product-hostile for negligible saving, and NotiBot is a feature the product wants people to use heavily, not sparingly.
- **Decision**: the only AI cost control is a **hard spend cap on the OpenAI and Groq accounts** (roadmap #40, rescoped). Reasoning that survives independent of the cost math: an in-memory limiter does not share state across serverless instances, so the app-level control was weaker than it looked; and `/api/chat` already degrades correctly when a provider refuses, returning real headlines via `degradedResponse()` rather than a 502. The failure mode of no limit is therefore a bill, not an outage.
- **Risk accepted, explicitly**: the application will record **nothing** about its own AI spend. `lib/ai-processing/call-ai.ts` continues to discard the provider `usage` object at all five call sites, so no spend is attributable to any user, agent or cron. There is no in-app lever to stop spend — the only lever is the provider dashboard, and it requires a human to be watching it. `/api/chat` also remains unauthenticated, so the abuse path (a script in a loop, ~$180/hour at sustained volume) is closed only by the provider's cap and not by anything in this repository. This was raised before the decision and the decision was taken with it on the table.
- **What was separated and lost anyway**: metering and enforcement are independent halves, and only enforcement was objectionable. Metering-only — persist `usage`, attribute per actor, build no gates — was offered and declined in favour of cancelling the subsystem outright. Re-open #54 as a metering-only row if per-call attribution is ever wanted; the design is recorded in the cancelled rows.
- **Consequence for M1**: the mission's phase 0 shrinks. Rate-limiting `/api/chat` was listed there as shipping first and independent of the identity work; it no longer ships at all. The identity phases (#41–#52) are unaffected — none of them depended on the ledger.

## 2026-09-04 — Partial re-reversal: metering returns, with a global budget in the environment

Third and current position on AI cost control today. The two earlier entries stand unedited above so the sequence is legible: the M1 sign-off specified metering plus per-user quotas plus a kill-switch; the reversal cancelled all of it; this entry restores the metering and adds a global ceiling, and leaves the per-user half cancelled.

- **Decision**: a **global** monthly budget per provider, configured in the environment — `OPENAI_MONTHLY_BUDGET_USD` and `GROQ_MONTHLY_BUDGET_USD`, defaulting to `5`. `callAI` sums the calendar-month `AiUsage` cost for that provider and refuses before the call when the budget is reached. At roughly $0.001 per message this is about 5,000 messages per provider per month.
- **Decision**: **no per-user limit anywhere**, unchanged from the reversal. A reader is never told they have used up an allowance, and `/api/chat` never returns a 429. An over-budget call reaches the existing `degradedResponse()` and gets real headlines instead of composed prose, which is the same degradation the route already performs when a provider is unavailable.
- **Why an env var needs the ledger back**: a budget the application enforces requires knowing the spend to date, so `AiUsage` (#53) is a hard prerequisite — a number in an env var with nothing to compare it against is decorative. This is why the cancellation could not stand once the budget was wanted in the environment rather than only in the provider console.
- **Two layers, deliberately**: the provider-console cap stays as the final backstop because it cannot be bypassed by any code path, including a bug in the check we are adding. The env var is the earlier, softer stop. Neither alone is sufficient — the console cap has no visibility and no graceful degradation, and the env var is only as correct as our own price table.
- **Correction of a fact repeated in the two entries above**: `callAI` has **3** call sites, not five — `app/api/chat/route.ts:119`, `lib/ai-generate-service.ts:222`, `lib/ai-processing/processor.ts:99`. The response body is already parsed into `data` inside `call-ai.ts`; only `data.choices[0].message.content` is returned, so `usage` is received and discarded rather than never fetched.
- **Blocked on the same hazard as the rest of M1 phase 1, and this is the operative constraint**: `AiUsage` is a new Prisma model, so it needs `prisma db push` against the shared Neon instance. Local and production are one database (`prod-db-differs-from-local`) and `prisma migrate deploy` never runs in CI (`prod-deploys-bypass-ci`), so there is no delivery path that is not a manual, deliberate write to production. The table is additive and cannot break existing reads, but it is still a production schema change and belongs to an operator, not to an agent mid-task.
- **Caveat recorded rather than assumed**: Groq's free tier does not bill, it rate-limits, so the console may have nowhere to accept a dollar cap. Layer 1 must not be reported as done for Groq until that is checked in the console.

## 2026-09-05 — The MCP server authenticates several clients, and four tools became confirmed actions

Two decisions taken together, because the second is only safe to take once the first exists.

- **Decision**: `/api/mcp` authenticates a **roster of clients** from `NOTILAB_MCP_CLIENTS_JSON`, one API key each, rather than the single `NOTILAB_MCP_API_KEY`. Abacus.ai and ChatGPT are two entries in that roster, not two endpoints. `lib/mcp/auth.ts` resolves the client identity **from the presented secret alone** — no header, tool argument or `clientInfo` field can influence it — and everything downstream already keyed off `identity.id`, so per-client audit attribution, rate-limit budgets and idempotency namespacing came for free rather than being built.
- **Rejected: a route per client** (`/api/mcp/abacus`, `/api/mcp/chatgpt`). A per-client route is a per-client code path, and a per-client code path is where an editorial rule eventually gets implemented twice. One endpoint, several credentials.
- **Rejected: OAuth**, for now. The MCP spec's authorization framework needs an authorization server NotiLab does not have, plus dynamic client registration and PKCE. A per-client static key already delivers independent identity, permissions, revocation, audit and rate limiting — the five properties the multi-client work was for. Recorded as limitation 5 in `docs/mcp.md` with the trigger to revisit: a client platform that requires OAuth, or third parties rather than the operator registering clients. Only `lib/mcp/auth.ts` changes when that day comes, because `executeToolCall` receives an `AgentIdentity` and does not care how it was proven.
- **Two roster rules that fail loudly rather than guessing**: a duplicate client id is dropped, and **two clients sharing an apiKey causes both to be refused** — if either were accepted, no request could be honestly attributed, which is the one thing the whole change exists to provide.
- **Backward compatibility is deliberate and temporary**: `NOTILAB_MCP_API_KEY` / `_AGENT_ID` / `_PERMISSIONS` still work and **coexist** with the roster, so the migration has no window in which MCP is down. They are a migration path, not a second supported shape.

- **Decision, and this one changes existing behaviour**: `approve_article`, `publish_article`, `unpublish_article` and `archive_article` now require **confirmation**. Before this, `lib/agent/confirmation.ts` existed and **no tool declared a policy**, so the gate had never once fired. The classification lives in `lib/agent/critical-actions.ts`, is attached to the tool declarations, and therefore applies to `/api/agent` exactly as it applies to MCP — a gate that were stricter on one transport is a gate an agent can shop around.
- **What makes those four critical** is not irreversibility — `unpublish` and `approve` are both walk-backable — but blast radius outside NotiLab. `reject_article` is terminal and deliberately **not** critical: it removes a story that was never public, and adding it would train agents to treat the confirmation step as noise.
- **Honest about what the gate buys**: the token is an HMAC of `(clientId, tool, validated input)`, so it proves *payload integrity* — it cannot be replayed onto different arguments or by a different client, both tested — but it does **not** prove a human approved. An autonomous client can read the token out of the refusal and repeat the call itself. What is gained is visibility (two audit rows, `confirmation: {required, satisfied}`), a hook for a client's confirmation UI, and that a looping agent cannot publish on its first misfire. Real human approval needs an approval queue with an identity attached; this is the seam for it, not the thing itself.
- **`NOTILAB_AGENT_CONFIRMATION_SECRET` must now be set.** With it unset the HMAC falls back to a constant, which was harmless while no policy fired and is not any more.
- **Escape hatch, per client rather than global**: `"skipCriticalConfirmation": true` on a roster entry. Opt-out, so a client configured by someone who never considered confirmation gets the gate. Intended for an unattended internal pipeline whose operator has accepted the risk; exempting one client does not affect any other.
- **Known breakage accepted**: any client already driving `/api/agent` or `/api/mcp` through those four tools needs the two-call flow before it can publish again. Three existing tests asserted the old single-call behaviour and were updated rather than the decision softened. Over MCP the token travels in `_meta["notilab/confirmationToken"]`, not in `arguments`, because every tool advertises `additionalProperties: false` and a strict client would drop an undeclared argument — this closes what `docs/mcp.md` previously listed as limitation 4.
