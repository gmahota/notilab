## 2026-07-13 — Quality gate RED→GREEN: root causes and fixes

Follow-up to the "Quality gate verification found the build currently broken" entry below — all five points there are now resolved; `pnpm lint` / `pnpm typecheck` / `pnpm build` pass. What actually fixed each:

- **`next lint`**: the real root cause was two *independent* dependency drifts, not just the `eslint` major bump. `eslint-config-next` had also been bumped `15.1.0 → 16.2.9` — a version meant for Next 16, mismatched with this project's `next@15.5.19`. That version is flat-config-only (ships no legacy `.eslintrc.json` support) and pulls in `eslint-plugin-react-hooks@7`, whose new experimental rules (`react-hooks/set-state-in-effect`, `react-hooks/purity`) flagged ~7 unrelated pre-existing components (routine "fetch in `useEffect`, then `setState`" patterns, and `Date.now()` calls in render). Migrating to flat config + `eslint .` (the officially suggested path) made lint *run*, but immediately hit that wall. The actual fix was simpler: pin `eslint-config-next` to `15.5.19` (matching the installed `next` version — Next's own docs say to keep these in lockstep) alongside `eslint` `^9.35.0`, and keep `next lint` + `.eslintrc.json` as-is. Lesson: when a lint tool breaks after a dependency bump, check *all* the packages that moved together, not just the one whose bump message mentions the error — `eslint-config-next` moving two majors ahead of `next` itself was the actual trigger, the ESLint 10 bump on its own was incidental (its plugins don't support ESLint 10 yet either — `pnpm install` surfaces this as peer-dependency warnings if you look).
- **Duplicate component exports**: `components/paste-link.tsx`, `social-share.tsx`, `news-feed.tsx` each had two full implementations concatenated in one file. Traced via `git show <commit> -- <file>` to a "feat(growth): viral loop..." commit that added a redesigned version of each component but didn't delete the old one (likely a bad merge/rebase, not a hand-written duplicate). Kept whichever version was actually wired up to current call sites (checked via cross-file usage, e.g. `news-card.tsx`'s `<SocialShare title url>` call only matches one of the two prop shapes).
- **Removed `lucide-react` brand icons**: current `lucide-react` (^1.14 range → resolved 1.24) dropped `Twitter`/`Facebook`/`Instagram`/`Linkedin`. Swapped to semantically-close generic icons already in the package (`X`, `Globe`, `Camera`, `Briefcase`) rather than adding a new icon dependency.
- **`ExperimentConfig` was missing real schema fields**: `lib/growth/experiments.ts`'s hand-maintained `ExperimentConfig` interface (used because `lib/prisma.ts` is a mock client — see below) only declared `{id, name, isActive, variants}`, even though the real `GrowthExperiment` Prisma model (`prisma/schema.prisma`) has `description`/`startedAt`/`endedAt` too. Consuming code (`lib/admin/experiment-results.ts`) worked around the gap with `as { startedAt: Date }`-style casts, which TS correctly flagged as unsafe (insufficient type overlap). Fix was to widen the interface to match the real schema instead of casting around it — the cast was treating a documentation gap as a type problem.
- **`lib/prisma.ts` is a mock client** (`export const prisma = mockPrisma as any`, per its own comment: "until it can be properly generated"). This is why every `lib/*.ts` file that touches models beyond `news`/`user`/`category` declares a local `PrismaExt = typeof prisma & {...}` cast — and why `.map()`/`.filter()` callbacks on those query results kept needing explicit parameter type annotations: `typeof prisma` is `any`, so `any & {...}` collapses the whole intersection back to `any`, silently swallowing every property access except bare, unannotated callback parameters (which `noImplicitAny` still flags). Out of scope for this pass (the mock itself is a separate, larger decision), but worth knowing before "just add a cast" becomes the default move on the next `PrismaExt`-shaped error.
- **Lockfile**: removed the stale, git-tracked `package-lock.json` (predated the `*-lock.json` gitignore rule, so it was never actually excluded) and committed a real `pnpm-lock.yaml`. Narrowed `.gitignore` from a blanket `*-lock.yaml`/`*-lock.json` pattern to exact-name `package-lock.json`/`yarn.lock` — the blanket pattern was also matching (and would have kept excluding) `pnpm-lock.yaml`, which CI's `pnpm install --frozen-lockfile` needs committed to do anything. Lesson: a "ignore all lockfiles" gitignore pattern is a footgun the moment a repo picks one package manager to actually commit.

## 2026-07-13 — Quality gate verification found the build currently broken

Running `pnpm lint` / `pnpm typecheck` / `pnpm build` for the first time while documenting the quality gate (see `docs/manager/quality/QUALITY_GATE.md` § Current status) revealed the gate is actually RED on `main`, unrelated to the governance files added this session:

- `next lint` is incompatible with ESLint 10 (passes CLI flags ESLint 10 removed) — likely from the `eslint 9.35.0 → 10.5.0` dependabot bump (PR #43) landing without migrating off `next lint`.
- `components/paste-link.tsx`, `components/social-share.tsx`, `components/news-feed.tsx` each have their component defined/exported twice in the same file — breaks both `tsc` and the webpack build.
- `components/quick-actions.tsx`, `share-panel.tsx`, `social-integrations.tsx`, `social-media-manager.tsx` import brand icons (`Twitter`, `Facebook`, `Instagram`, `Linkedin`) that the installed `lucide-react` version no longer exports.
- `lib/ai-processing/processor.ts` / `save-result.ts` import `prisma` as a default export; `lib/prisma.ts` only exports it as a named export.
- No `pnpm-lock.yaml` is committed (only a stale npm-era `package-lock.json`, tracked despite matching the `*-lock.json` gitignore pattern) — `pnpm install --frozen-lockfile` in CI has nothing to freeze against.

Lesson: dependency bumps (via Dependabot or otherwise) that change a tool's CLI contract (ESLint major versions especially) need a smoke-test run of the actual `pnpm lint`/`build` commands before merging, not just a green "install succeeded" signal. This also means `cto-review.yml`'s scripted checks and `ci-cd.yml`'s lint/typecheck/build jobs have likely been failing on recent CI runs — worth checking Actions history to confirm since when. Tracked as roadmap item #5.

## 2026-07-13 — AI governance bootstrap

- **Package manager drift**: `README.md` documented `npm` while `.github/copilot-instructions.md` and all CI workflows already used `pnpm`. Standardized on `pnpm` everywhere (see `AGENTS.md`); fixed `README.md`. Lesson: when a stack-defining file (Copilot instructions, CI) picks a convention, propagate it to user-facing docs immediately, don't let them drift.
- **No test suite exists**: no Jest/Vitest/Playwright, no `*.test.*` files, `package.json` has no `test` script. The quality gate (`docs/manager/quality/QUALITY_GATE.md`) was deliberately scoped to lint + typecheck + build + security scans (all already enforced by existing CI) rather than pretending test coverage exists. Lesson: don't let governance docs claim more rigor than actually exists — document the real gate, and list test coverage as an explicit Phase 2 addition instead of a silent no-op.
  - **Superseded 2026-09-03.** Jest was added during the Agent Management API work, but the reverse of the original lesson then happened: three governance files (`AGENTS.md` § Testing Rules, `QUALITY_GATE.md`, this entry) went on asserting *less* rigor than existed for weeks, and roadmap item #13 was scoped as a framework bootstrap when it was really a coverage gap. Corrected lesson: a claim about tooling is stale the moment the tooling changes, in **either** direction — the file that says "there is no X" needs updating by whoever adds X, and "no X" is exactly the kind of claim readers act on without re-verifying.
- **ESLint config contradicts stated convention**: `.eslintrc.json` disables `@typescript-eslint/no-explicit-any` and `no-unused-vars`, while `copilot-instructions.md`, `.github/PULL_REQUEST_TEMPLATE.md`, and the `cto-review` prompt all say to avoid `any`. The rule is currently unenforced by tooling. Lesson: a stated convention with no enforcing lint rule will erode — worth tightening the ESLint config in a future pass rather than relying on agents/reviewers to catch it by hand every time.
  - **Partly resolved 2026-09-03**: both rules are now `"warn"`. The erosion was measurable when the rules were finally switched on — **81 violations across 37 files**, i.e. roughly a third of the app/lib surface, accumulated in the window where the convention was written down but unenforced. That number is the concrete cost of the gap between a documented convention and a configured one, and it is also why the flip had to be `"warn"` rather than `"error"`: by the time you notice, the backlog is too large to clear in the same change. Turn a convention on the day you write it down, when the violation count is zero.
- **`.lighthouserc.json` is orphaned**: present in the repo root but not referenced by any GitHub workflow. Either wire it into CI or remove it — an unused config file reads as intentional and misleads whoever finds it next.
  - **Resolved 2026-09-03**: removed rather than wired in (wiring it means adding a CI tool, which `AGENTS.md` § Dependency Policy gates behind a discussion). Its thresholds are recorded in `decisions.md` so deleting the file did not delete the intent. Lesson extension: when removing an orphaned config, move its content into a decision record first — otherwise the deletion looks like the feature was rejected, when it was only deferred.

## 2026-09-04 — Scanning for Portuguese leftovers: word lists and accent grep both under-count

Part of the language-convention sweep (roadmap #23–#32). Three successive scans of the same codebase found increasing numbers of violations: a Portuguese *word list* grep found 1 comment, an accent-character grep found 14, and a third manual pass found 3 more — including two in `prisma/schema.prisma`. Unaccented Portuguese (e.g. `// Implementar uso do template`, `buscados:`, `PORTA DE QUALIDADE`) is structurally invisible to a diacritic-based grep, and a word list only ever finds words someone thought to include. The reliable method is to **enumerate every comment/string and read it**, not to grep for suspicion — a targeted grep is a fine first pass but cannot be the last one. A half-translated file is worse than an untranslated one: one operator-facing script ended up with mixed-language output in a single report because its scope was set from the accent-grep pass alone.
